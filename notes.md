# CSRF Notes

# CSRF

CSRF =

# Cross Site Request Forgery

Example:

You are logged into a trusted website.

Then you visit some malicious website like:

```text
download-free-movie.com
```

That site secretly sends requests using your active session/cookies.

If server trusts that session, attacker can perform actions as you.

Example:

- Change password
- Transfer money
- Delete account

without your permission.

---

# Why Session Matters

After login, browser stores:

# Session ID

like:

```text
JSESSIONID
```

Browser automatically sends this cookie with requests.

Attacker tries to misuse this authenticated session.

---

# CSRF Protection

Spring Security adds:

# CSRF Tokens

to prevent fake requests.

Server checks:

```text
Is this request coming from trusted frontend?
```

---

# Where CSRF Matters

Mostly for:

- POST
- PUT
- DELETE

because they:

# Change server state

Examples:

- Updating profile
- Sending money
- Deleting data

---

# Why Not GET?

GET requests should only:

# Fetch Data

and not modify anything.

So CSRF protection usually focuses on state-changing requests, not GET requests.

# Spring Security Advanced Notes

# Sessions and CSRF

After login, server creates:

# Session Object

which stores:

- User details
- Authentication details

Server also creates:

# Session ID

and sends it to browser.

Browser stores it inside:

# Cookies

Example:

JSESSIONID

Browser automatically sends session ID with every request.

Server verifies session ID using stored session object.

---

# CSRF Problem

Malicious websites can misuse browser cookies/session.

To prevent this, Spring Security uses:

# CSRF Token

Frontend sends token generated by same trusted site.

Server verifies token before accepting:

- POST
- PUT
- DELETE

requests.

---

# SameSite Strict

Another protection mechanism:

# SameSite=Strict

prevents browser from sending cookies during cross-site requests.

This reduces CSRF attacks.

---

# Accessing CSRF Token

CSRF token can be accessed using:

# HttpServletRequest

inside controllers/filters.

Used on class.

# formLogin()

http.formLogin(Customizer.withDefaults());

Enables:

# Form Based Login

Spring automatically creates:

/login

HTML login page.

Used mostly for:

# Web Applications

After login:

- Session created
- Cookies used

---

# httpBasic()

http.httpBasic(Customizer.withDefaults());

Enables:

# HTTP Basic Authentication

Credentials sent in:

Authorization Header

No login page involved.

Mostly useful for:

- APIs
- Postman testing

---

# formLogin vs httpBasic

## formLogin()

- Browser login form
- Session + cookies used
- Best for frontend web apps

---

## httpBasic()

- Credentials sent every request
- No UI login page
- Good for REST APIs

---

# Stateless Sessions

SessionCreationPolicy.STATELESS

means:

# No server-side sessions.

Spring does NOT remember users between requests.

Every request must carry authentication again.

Common for:

- REST APIs
- JWT Authentication

Without credentials:

401 Unauthorized

comes.

---

# formLogin + Stateless

Normally form login creates session.

But in stateless mode:

Session not stored

So user must authenticate again every request.

That makes formLogin less useful in stateless APIs.

---

# httpBasic + Stateless

Works well together because:

- Basic Auth already sends credentials every request
- No session needed

Perfect for stateless REST APIs.

# Multiple SecurityFilterChain

One `SecurityFilterChain` bean = one filter chain configuration.

Multiple `SecurityFilterChain` beans = different security rules for different URL patterns.

Example idea:

```text
/api/**      -> API security rules
/admin/**    -> Admin security rules
/public/**   -> Public routes
```

Different URL groups can use different filters/configurations.

# UserDetailsService

`UserDetailsService` is an interface used by Spring Security to:

# Load User Details

during authentication.

It fetches:

- Username
- Password
- Roles/Authorities

usually from DB.

---

# UserDetailsService Workflow

1. User sends credentials.
2. AuthenticationManager receives them.
3. Calls:

loadUserByUsername(username)

4. UserDetailsService checks DB.
5. Returns UserDetails object.
6. PasswordEncoder compares passwords.
7. If valid → Authentication success.
8. SecurityContext updated.
9. If invalid → 401 Unauthorized.

---

# UserDetailsService Implementations

We can:

## 1. Create Custom Implementation

Implement `UserDetailsService` ourselves.

Useful for:

- Database authentication
- Custom logic

---

## 2. Use Built-in Implementations

Spring already provides:

- InMemoryUserDetailsManager
- JdbcUserDetailsManager

---

 # *****IMPORTANT WORKFLOW OF FORM LOGIN WITH DATABASE*****

1. User submits login form.
2. UsernamePasswordAuthenticationFilter intercepts request.
3. AuthenticationManager receives credentials.
4. AuthenticationProvider handles authentication.
5. Provider calls:

loadUserByUsername(username)

6. DB queried for user details.
7. UserDetails returned.
8. PasswordEncoder compares raw vs encoded password.
9. If matched → Authentication success.
10. User stored in SecurityContext.
11. If failed → 401 Unauthorized / login failure.

# Old Way (Spring 5)

We usually:

# Implemented UserDetailsService manually

inside separate class.

That class:

- Queried DB
- Returned UserDetails object

Spring automatically plugged it into:

# DaoAuthenticationProvider

Workflow:

```text
Filter
  ↓
AuthenticationManager
  ↓
DaoAuthenticationProvider
  ↓
Your UserDetailsService
  ↓
Database
```

---

# New Way (Spring 6)

Now Spring encourages explicit configuration.

We configure:

# AuthenticationProvider Bean

usually:

# DaoAuthenticationProvider

This provider internally uses:

- UserDetailsService
- PasswordEncoder

Workflow remains same:

```text
Form Login
   ↓
Filter
   ↓
AuthenticationManager
   ↓
AuthenticationProvider
   ↓
UserDetailsService
   ↓
PasswordEncoder
```

---

# Important Point

If you want:

- DB authentication
- Custom lookup logic

then YES:

# You still implement UserDetailsService

and override:

loadUserByUsername()

The difference is:

In Spring 6, you explicitly wire it into AuthenticationProvider bean.

---

# Simple Summary

## Spring 5

Mostly:

- Implement UserDetailsService
- Spring auto-configures provider

---

## Spring 6

Mostly:

- Configure AuthenticationProvider bean manually
- Wire UserDetailsService + PasswordEncoder explicitly

# Custom Queries in Spring Data JPA

Custom methods can be added in 2 ways.

---

## 1. Simple Queries

Declare methods directly in repository interface.

Spring automatically generates queries using:

- Method names
- @Query annotation

Useful for:

- Simple searches
- findByName()
- findByBrand()

---

## 2. Complex Queries

Create:

- Custom repository interface
- Separate implementation class

Use:

- EntityManager
- Native queries
- Complex JPQL

for advanced database logic.

Spring combines:

- Auto-generated repository methods
- Custom implementation methods

together automatically.

---

# Simple Takeaway

## Simple queries

→ Declare directly in repository interface.

## Complex queries

→ Create separate implementation class.
